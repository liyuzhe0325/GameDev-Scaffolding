# 按需专业研究：GameDev Scaffolding 核心策略

状态：已确认的设计方向，机制尚待实现与验证。2026-10-30。

## 核心决定
**不要预先研究完每个专业的所有知识。** 横向职业地图是能力导航、问题触发和工具索引，纵向生命周期地图是时机和交付约束，生产调用链是专业协同。遭遇真实问题时才开展所需深度的专项研究。

## 预先建设的内容
- 岗位与细分能力清单：能解决什么、典型输入输出、与谁协作。
- 问题触发器：哪些现象意味着需要调用哪种专业能力或查证事实。
- 外部工具索引：原生/成熟工具优先，列出能验证什么及盲区。
- 生命周期触发点与完成标准：什么时候需要，什么证据足够。
- 经验库：只保存带来源和适用条件的实际决策事件，而非泛化口号。

## 任务到研究的循环
1. 观察当前目标与工程/设计事实，发现候选问题。
2. 判定重要性与时机，避免把所有局部缺口都立刻执行。
3. 用横向/纵向地图识别相关专业、工序、依赖和知识缺口。
4. 判断下一步是直接执行、读取工具事实、向用户询问创作意图，还是定向研究。
5. 定向研究时优先读取当前工程、官方资料、一手开发经验和适当工具；明确问题与研究范围。
6. 实验、推导或实际运行验证方案，不把资料摘要当作验证。
7. 有足够证据解决当前问题时停止研究，回到生产；保留尚待验证事项。
8. 将原始证据、决策、失败和可复用触发条件写入经验库，按需更新地图。

## 研究深度自适应
- L0：直接应用已验证经验。
- L1：查询专业地图、项目事实和现成工具。
- L2：针对特定缺口阅读资料、比较案例、构建有限实验。
- L3：遇到重大风险或现有方法失败，开展理论/机制级深度研究。
不要因能深入而深入；深度由风险、当前证据不足和任务价值决定。

## 必须避免
- 逐岗位编写“专业百科全书”；
- 研究结论脱离具体任务而无限拓展；
- 用 LLM 短期上下文维护权威工程事实；
- 发现问题就新建工具或 Manager；
- 把研究成果数量当作项目价值；
- 没有明确完成标准就无限搜索。

## 第一项验证
以“门与建筑职责冲突”为案例：观察 Agent 能否先查询现有领域事实，再触发必要的架构专项研究，生成最小方案并明确停止条件。与无地图/无研究路由的基线对照，比较重复状态、集成正确率、Token 和返工次数。

## 与旧文档关系
R1–R7 及现有深度专题保留作资料索引和方法样本，**不要求继续逐岗位等深度研究**。此前 Research Depth Gate 不应解释为每个岗位都必须先达到 L3 才能使用；仅适用于启动深度研究后对质量与证据的要求。
