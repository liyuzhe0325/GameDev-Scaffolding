# Open-source Solution Navigation R1

日期：2026-10-30。性质：已检查上游资料的技术选型与研究路线，**未安装/集成**工具。

## 目标
让已有 Hermes/Codex 在接到游戏开发目标时，先逆推关键条件，再沿开源生态发现成熟方案、真实源码、测试和已知局限。Scaffolding 提醒和路由，LLM 负责推理，不自建第二套 Agent 大脑。

## 复用优先路线
目标 → 条件假设 → 检查当前项目已有能力 → 搜索成熟开源项目/官方样例 → 阅读真实实现和测试/Issue/PR → 评估适用条件与许可 → 选择直接集成/局部借鉴/仅参考原理 → 执行验证。

### 重要纪律
- “相关仓库”并非“解决问题的仓库”；README 声称不是代码证据。
- 不按 Star 数直接选择；核对维护、实际能力、测试、许可、依赖、目标平台和版本。
- 外部代码视为不可信输入；不盲目执行仓库脚本，不输入密钥。
- 明确区分直接复制代码（需审查许可证）与学习算法/实现思路。
- 现有项目能力优先；新框架需要清楚说明现有方案不能满足什么。

## 最小工作机制
1. 简短提醒：复杂任务先问“最终行为要成立，缺什么条件？现成方案在哪里？”。
2. 轻量能力节点：领域、触发问题、参考搜索入口和验证方式。只按需加载。
3. 检索：优先现有代码/官方样例/成熟仓库；没有足够证据才深挖。
4. 结果记录：只记录导致方案改变的发现，附来源、适用前提和验证状态。
5. 完成：满足目标且必要验证足够就停止，不积累无关研究报告。

## 方案筛选判断
- 功能匹配与源码证据；
- 与引擎/版本/许可证兼容；
- 项目维护与已知问题；
- 适配成本对比自研；
- 与现有架构的关系；
- 可测试的验收条件。

## 待验证
- Agent 是否能从模糊目标搜索到正确的开源工程，而不依赖用户给术语？
- 阅读实现与 Issue/PR 后能否发现原先遗漏的前置条件？
- 能否避免将某实现方式误标为必要条件？
- 相比只给逆推提醒，加载能力索引是否带来额外价值？
- Serena 在具体 Unity 工程中的 C# 索引是否完整？

目前结论是**值得试用的工具组合**，不是已证实的性能提升。
