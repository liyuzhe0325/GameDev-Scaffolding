# Goal Regression & Capability Routing（GRCR）R1

日期：2026-10-30。状态：**设计协议与待验证假设**，不声称已实现 Agent、已验证能力检索或修改《巨楼》。

## 要解决的不是“知识越多越好”

用户指定目标后，应先**逆向求解满足目标需要什么条件**，再识别已有项目能力与外部人类成熟方案，只有没有被满足的条件才需要进一步研究/实现。

> 目标 G → 验收谓词 → 必要条件或替代路径 → 当前事实匹配 → 专业能力路由 → 成熟方案查询 → 适配/实验 → 验证 G。

**两种图不要混淆**：
- **目标依赖图**：有方向，边表示“实现 G 在给定方案和上下文下需要 C”，涉及 AND（必须全部满足）/OR（可替代路径）、约束和验收。
- **专业能力/资料图**：提供“找谁、搜什么、用什么工具”的路标，不能因两概念相关就说它们之间有必要依赖。

## 真实规则与假设边界

- 逆向链式推理对给定规则有用；开放式游戏制作的规则常常不完整，LLM 的“必要条件”只是待证假设。
- 不能把所有可能相关的专业都强制展开；只针对当前候选实现路径及已发现风险。
- 不能从“有需求”直接推断“需要新代码”：先查询当前项目事实、已有工具、已验证的经验和公开成熟方案。
- 即使局部需求可以满足，也必须检查是否破坏更高层的结构约束。
- 不允许“开始研究”演变为无限搜索：每次研究有具体未解条件、证据缺口、搜索预算、停止条件。

## 依赖节点（初版最小结构）

```yaml
id: G-001
goal: "玩家能在管道中被怪物追逐"
acceptance:
  - "在指定测试场景中，怪物可进入目标管道并抵达玩家可达的位置"
  - "不同体型与状态不会穿模或错误穿墙"
  - "玩家能观察到与玩法规则一致的追逐反馈"
requirements:
  operator: AND
  members: [COND-TRACK, COND-TRAVERSE, COND-FEEDBACK]
alternatives:
  COND-TRAVERSE:
    operator: OR
    paths: ["复用现有导航+特殊动作", "专用管道节点/链接"]
condition_status: unknown # satisfied | unsatisfied | unknown | blocked
evidence: [] # 源码、实际运行、官方文档、项目决定等
capability_routes: [] # 专业能力节点 ID
solution_candidates: [] # 方案 + 适用条件/来源
research_budget: "只调查本条件，满足验收后停止"
```

这不是最终数据库 schema，先用于人工/LLM 研究记录；正式方案须验证后再定。

## 推理流程

**R0 约束**：确认目标、用户授权、当前阶段/质量目标；不追问专业未知，只在不可替代的创作选择时请用户决定。

**R1 目标可验收化**：把自然语言描述变为可观察条件，保留主观体验部分的人工验收；不能把局部子目标当成最终目标。

**R2 逆向展开**：提出最小 AND 必要条件，针对不同实现路径列 OR 备选，并记录条件的真实性假设、是否能反证、适用上下文。

**R3 条件匹配**（核心）：先查当前项目已有结构、工具、资源、工作流、经验；把每一条件标记为“已满足/未满足/未知”，附证据及失效条件。未知不等于未实现。

**R4 触手导航**：使用横向岗位图找到能力，纵向流程图找到工序与验收，并关联到文献、工具、开源方案；路由是检索指南，不是技术答案。

**R5 方案获取与适配**：从官方文档、成熟开源、开发者一手经验中找既有方法。分别标明“可直接复用/需要适配/不适合/证据不足”。

**R6 定向研究**：仅对关键未解条件进一步搜索、比较或实验；多余领域暂缓。工具能确定性检查的事实不让 LLM 凭空推测。

**R7 组合与一致性验证**：执行前再次检查是否重复权威状态、制造新架构、引入未授权设计变更；运行测试包括单点和整个用户目标。

**R8 完成及经验回流**：验收成立且未触发上级约束，结束当前研究；保存有效路径、证据、失败边界与未来可触发条件。若失败，回到最先被证伪的条件，而不是重新生成一套空泛计划。

## 停止/继续判定

- **停止搜索**：已有可验证方案，关键条件覆盖充分，继续搜索预期收益低。
- **转向工具查询**：需要的是现有工程事实或数学/静态可判定信息。
- **转向专项研究**：多个可信方案冲突、关键条件来源不明、风险高。
- **停止开发**：本阶段验收已达到，新增抽象只服务假想未来。
- **回退重评**：整体可玩目标或结构约束与局部方案冲突。

## 反例：为什么不直接做 GraphRAG

知识图能帮助找到相邻概念，但“相关”不等于“必须”。我们的决策主轴应是带验收的目标条件图；GraphRAG/搜索只是获取事实和方案的可替换工具。没有对照优势前，不选数据库或自建图谱平台。

## 研究参考

- NVIDIA Nemotron-CORTEXA：以代码实体图和调用关系辅助定位，提高了相对其论文基线的召回率，但无法自动证明领域语义正确：https://research.nvidia.com/labs/adlr/cortexa/
- SWE-Explore（2026）：专门评价仓库探索质量与效率，说明“能正确定位现有能力”本身可成为独立指标：https://huggingface.co/papers/2606.07297
- SWE-rebench（NeurIPS 2025）：强调真实交互软件工程任务与环境反馈，不应仅用一次性代码生成成功判定能力：https://proceedings.neurips.cc/paper_files/paper/2025/hash/21bec6ace947b1b58967b945c8ac0f10-Abstract-Datasets_and_Benchmarks_Track.html

## 研究产物

下一步不是实现一个全新 Agent：先在 3–5 个有明确既有能力与隐含依赖的任务上，用同一模型分别进行普通方案和 GRCR 引导方案，对比**条件覆盖、已有能力正确识别、冗余新建、真正集成成功、搜索开销与停止时机**。
