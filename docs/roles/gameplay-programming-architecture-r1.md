# Gameplay 程序与架构技术负责人：现有工程变更的专业实践 R1

状态：证据研究 + 可验证的工程设计提案；未在《巨楼》当前代码上运行实验。日期：2026-10-30。

## 1. 要解决的现实问题

LLM 编码时可能将“新增门功能”误解为“从零开发一套门领域”，继而新建 Manager、Registry、状态和空间拓扑。每个局部决定看似合理，却可能复制建筑系统已有的职责。

关键不是禁止抽象，也不是强制单体架构，而是**验证原有领域模型与新改动之间的契合程度**。

需要区分四类现象：
- **重复权威状态**：多个模块对相同业务事实独立读写；
- **重复派生数据**：可容忍，但必须有明确权威源和失效/同步机制；
- **合理的专业分层**：同一业务对象的不同职责分离，不视为重复；
- **虚假通用化**：尚无第二个用例，就因想象未来需求而创建深层框架。

## 3. 外部工具的分工

### 可靠事实层
- Roslyn / LSP：符号定义、类型与引用（须验证项目加载完整）。
- Tree-sitter / repository map：跨仓库低成本浏览，适合作导航。
- Unity AssetDatabase：资产层的静态引用（不能据此推断所有运行时关系）。
- Git：变更范围、历史决策线索（历史提交不等于正式设计意图）。
- 编译器/静态分析器：结构化诊断与可执行代码规范。
- EditMode/PlayMode 测试、场景运行：真实行为证据。

### 仍需专业推理
- 是否属于同一个领域概念；
- 何种数据是事实权威、何种只是缓存；
- 新建模块是否在业务上必要；
- 性能与可维护性之间何时应取舍；
- 玩家体验和设计意图是否满足。

## 4. 先查事实再写代码：最小变更协议

1. 描述**可观察的目标行为**，不要预设新增管理器。
2. 搜索现存同义/关联概念和跨模块接口，检查索引是否完整。
3. 列出实际代码/资源证据：符号位置、调用关系、数据状态及职责边界。
4. 绘制小范围影响图：读写者、事件、序列化与场景引用。
5. 列出两种以上实施方案并说明新增抽象的必要性。
6. 实施最小可用改动，同时建立必要回归测试。
7. 执行构建、静态规则、实际场景与跨系统测试。
8. 在提交说明中写清变更、影响和未验证部分。

**退出原则**：若已有扩展点可以完成当前需求，不能仅因“未来扩展性”而增设平行的事实来源；若新增模块确有独立、稳定职责，允许建立。

## 5. 证据与局限

- Aider 团队说明 repository map 使用 Tree-sitter 提取重要类/函数，并选择与当前上下文相关的符号，目的是减少全量源码加载负担。https://aider.chat/2023/10/22/repomap.html
- Unity 官方提供 Roslyn analyzers 和基于 asmdef 的诊断作用域，支持部分代码规则的自动化。https://docs.unity.cn/6000.1/Documentation/Manual/analyzer-scope-and-diagnostics.html
- 微软 Unity Analyzers 提供 Unity 特定诊断/抑制器，需进一步查看版本兼容和规则覆盖。https://github.com/microsoft/Microsoft.Unity.Analyzers
- Codebase-Memory 的实验显示图谱降低成本但不能完全替代源码探索；论文报告 31 仓库对照下 83% vs 92% 回答质量、约 10x Token 节省和 2.1x 工具调用减少。https://arxiv.org/abs/2603.27277
- 本文没有把“静态工具能自动检测所有重复领域概念”当成事实：语义重复需要项目领域模型和人工/LLM 推理。
