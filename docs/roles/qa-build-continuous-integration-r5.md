# GDKM-Role R5｜游戏 QA、构建工程、持续集成与可玩版本守护

日期：2026-10-30。状态：**岗位与 Unity 工具能力已查证，具体工程流程是研究提案；未接触或测试《巨楼》本地工程**。

## 核心议题

编码 Agent 可以让一项功能的单元测试通过，却仍破坏 Prefab 引用、关卡通路、序列化和其他玩法。需要把“修改局部代码”改成“证明变更没有破坏关键可玩约束”，并从失败证据中主动发现新问题。

要区分四类结论：
1. 编译/静态规则通过；
2. 局部测试通过；
3. 跨场景集成与构建通过；
4. 目标玩家体验实际成立。

前三级工具可大量辅助，第四级必须结合试玩和专业判断；不能把“全绿”说成“游戏好玩”。

## 2. 纵向工序：每次代码变更的“证据通道”

| 步骤 | 触发 | 证据 | 不满足时的动作 |
|---|---|---|---|
| V-01 变更定位 | 计划实现新功能 | 源码和 Unity 资源依赖影响范围 | 先查证，不先生成框架 |
| V-02 静态检查 | 变更完成 | 编译错误、架构约束、序列化检查 | 回到相关程序/技术美术 |
| V-03 局部回归 | 静态检查通过 | EditMode/PlayMode 单模块测试 | 定位错误及归属 |
| V-04 跨系统回归 | 受影响核心交互 | 门状态↔建筑通行↔AI 导航↔Prefab | 补充跨专业测试 |
| V-05 Player 构建 | 达到构建门槛 | 构建配置、日志、版本、生成产物 | 修复构建与平台问题 |
| V-06 可玩冒烟测试 | 每个重要里程碑 | 玩家从起点到目标的关键路径实际可走 | 将瓶颈升级为主线任务 |
| V-07 试玩与审查 | 稳定可玩版本 | 玩家反馈、可读性、挫折/乐趣等 | 由设计/关卡/艺术共同调整 |
| V-08 经验回流 | 缺陷解决/返工 | 原因、失败检测点、修复证据 | 增加条件化规则而非模糊教训 |

**不能直接从提交时间推断功能完成**；必须保存构建与测试证据、版本 SHA 和目标平台。

## 3. Unity 官方工具核查

- Unity Test Framework 区分 Edit Mode 和 Play Mode；Play Mode 可跨帧执行行为测试；并支持在目标 Player 中运行部分测试。见：https://unity.com/how-to/automated-tests-unity-test-framework
- Unity 6000.5 支持通过命令行执行测试并输出 XML 结果，典型参数为 `-runTests -batchmode -projectPath ... -testResults ...`。见：https://docs.unity.com/en-us/engine/6000.5/manual/scripting/test-framework-introduction/running-tests/run-tests-from-command-line
- Unity 6000.x 支持命令行构建（`-buildTarget` 或 `-activeBuildProfile` 配合 `-build`），适用于持续集成。见：https://docs.unity.com/en-us/engine/6000.0/manual/building-and-publishing/build-command-line

**风险/待验证**：某些 Unity 批处理设置与包版本不同，实际命令、许可证、项目锁、平台模块和资源导入行为需由本地 Codex/Unity 实测。此研究不声称已创建 CI。

## 4. 要让 Agent 主动发现什么问题？

不止测试失败：
- 编译虽通过但核心场景不可运行；
- Door/Building 的逻辑连通成立，NavMesh 与实际碰撞不成立；
- 改动了动画状态但 Collider/Root Motion 不协调；
- 原有测试无覆盖，却新增了关键状态转换；
- 某次改动新增或复制一个权威状态源；
- 经常失败的人工操作可以用现有检查器自动化；
- 几个独立功能都成功，但缺少从开始到结束的可玩流程。

## 5. 首批建议验证的最小流程（仅提出方案）

**不要先自建 CI 平台**。在 Unity 6.5 本地工程，先检查是否已具备测试程序集，确认最小 EditMode 测试、一个 PlayMode 交互测试、一次 Player 构建能否获得结构化结果。再判断是否需要 GitHub Actions 或其他现有 runner。

建议的冒烟链：加载测试场景 → 角色移动 → 打开一扇门 → 穿过建筑连接点 → NPC 重新寻路 → 触发撤离。先记录可运行证据和缺口，不为了测试而重新实现建筑或门系统。

## 6. 测评框架

- **缺陷提前发现率**：有多少问题在变更提交前被发现。
- **误报率**：错误警报占比。
- **跨系统回归覆盖**：关键交接与状态转换是否得到测试。
- **构建可用率**：有多少提交能产生可运行版本。
- **修复成本**：复现、定位、修复需要多少次尝试。
- **主线可玩性**：玩家核心流程是否仍贯通。
- **认知负担**：LLM 工具调用、Token 成本、重复探索次数。
