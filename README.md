# GameDev Scaffolding

> 让 LLM 以专业游戏开发流程、真实经验和可靠外部工具为支撑，帮助创作者把想法做成完整、可玩的游戏。

**状态**：研究与架构定义阶段（2026-10-30）。本仓库记录设计决策和研究计划，不代表相关工具已完成集成。

## 愿景与定位

- **长期愿景**：从一句游戏创意出发，组织设计、制作、实现、集成、验证和迭代，最终形成可玩的游戏。
- **近期范围**：个人游戏开发辅助，首先以《巨楼》作为真实验证场景。现阶段不以商业化或通用平台为目标。
- **用户身份**：创作意图、重要取舍和授权的拥有者，可随时亲自参与任何专业环节；不强制充当项目经理或固定岗位。
- **核心问题**：LLM 不只缺知识，更难主动发现*应该考虑什么*、*什么才是当下问题*、*是否在重复已有抽象*，也难以在有限上下文中维护准确的全局项目认知。

## 已确认的设计原则

1. **专业经验优先**：先研究真实开发者/团队怎么工作，再选择工具与组织方案；不从多 Agent 框架开始。
2. **外部化可靠能力**（Externalize What Can Be Verified）：代码结构、资源依赖、项目状态、构建、测试、架构约束等尽可能由确定性工具生成与核验，避免依赖 LLM 临时记忆。
3. **先复用后自建**：直接复用 → 配置成熟工具 → 组合工具 → 证实存在缺口后才新开发工具。
4. **专业地图与项目地图分开**：行业方法说明“专业上通常怎么做”；实时项目地图回答“当前工程实际上是什么样”；不能以行业惯例覆盖项目事实。
5. **有据可查的经验蒸馏**：原始事实、开发者主张、系统推论分开；记录来源、时间、适用条件、反例和审查状态。
6. **跨专业生产闭环**：明确输入、依赖、职责归属、产物、验收、集成、返工与反馈；避免“每个功能都完成了但游戏仍不可玩”。
7. **防止局部抽象膨胀**：新功能先查已有领域模型/权威状态，识别重复实体、硬编码、管理器与数据源；不以测试通过等同架构正确。
8. **主动但有边界**：Agent 应主动发现缺口、提出验证与调研，也须判断何时暂停、询问用户或停止扩展；重大创作决策和未授权操作不擅自执行。
9. **研究不等于落地**：开源候选工具、工作室案例及知识图谱方案必须经原始资料核查与项目实测，不把概念推导表述为已验证事实。

## 知识架构

### A. 横向：GDKM-Role（职业与专业能力）

研究游戏设计、叙事、关卡、概念美术、3D 资产、绑定、动画、技术美术、VFX、引擎/图形、Gameplay/AI、音频、UI/UX、制作、QA、构建、发行等实际岗位。

每个职业节点记录：职责边界、工作对象、日常工序、关键专业判断、工具和资料来源、输入输出、验收、常见返工、协作关系、原始案例。

### B. 纵向：GDKM-Lifecycle（开发生命周期）

参考阶段：概念与立项 → 玩法原型 → 预制作 → 垂直切片 → 正式生产 → Alpha → Beta → 发布候选 → 发布 → 维护和复盘。实际阶段允许并行、返回与重叠。

沿五级展开：**阶段 → 工作流 → 任务 → 专业操作 → 验证与决策**。每个节点研究“做什么、为什么、需要什么前置、谁参与、用什么工具/网站、产出什么、怎么验收”。

### C. 组织：GDKM-Production（真实公司生产调用链）

研究目标提出、专业识别、跨部门可行性评审、选择生产组织模式、依赖分解、并行/串行制作、交付审查、集成验证、缺陷归因、返工和经验回流。

不同任务应采取不同模式：明确规格的资产交接；玩法探索与短循环原型；跨专业功能协作；量产内容；故障排查；项目集成。**不必将每个专业变为独立 Agent**。

### D. 生产对象与项目认知层

前三条线以实际交付物/生产对象（角色、门、场景、任务、战斗机制、可玩版本等）连结。项目认知层（PIL）由真实工程持续生成：

- 代码符号、引用和调用关系；
- Unity Scene、Prefab、ScriptableObject、模型、动画等依赖；
- 领域模型、状态权威、数据流和必要的运行时关系；
- 架构决策、Git 变更与历史；
- 编译、测试、构建、实际运行、性能和试玩证据。

**分层检索**：低成本全局摘要 → 按任务检索结构子图 → 必要时读取原始代码和资源。地图不替代源码阅读。

## GDED：真实游戏开发经验蒸馏

资料源：开发日志、专业教程、GDC 演讲、开发者访谈、幕后纪录片、Postmortem、Git 提交/PR、玩家测试反馈。

三种增长渠道：

1. **广域采集**：不依赖单一项目的持续资料发现与筛选。
2. **定向研究**：开发过程中由当前任务、未知风险和失败触发专项搜索。
3. **个人实测**：从自己的代码、实验、试玩、失败和修复中积累可复用经验。

经验最小单位是**有证据的决策事件**：目标及环境 → 当时问题 → 备选方案 → 实际选择 → 实际结果 → 开发者解释 → 我们的归纳 → 适用条件/例外 → 原始来源。保持案例事实与推论的区分。

潜在发现索引：IGDB（游戏目录）、MobyGames（制作人员/团队）、RAWG/Wikidata（补充关系）；这些是发现入口，不等于经验来源。

## 主动问题发现与整体收敛

Agent 需要区分：

- 是否真正存在问题；
- 对最终可玩目标有多重要；
- 是否应该现在解决；
- 是否缺乏知识、缺乏现实证据或需要用户创作决定；
- 继续研究会不会造成局部抽象膨胀；
- 是否已达到本阶段的“足够好”标准。

研究成果与工程成果都要能回溯到某个可验证的整体目标；探索性研究可独立存在，但需记录假设、研究边界、退出条件，不能自动吞噬主线。

## 外部工具：候选，不是既定技术栈

| 能力 | 优先考察的成熟工具/实践 | 需验证的事项 |
|---|---|---|
| 代码符号与引用 | Roslyn、LSP、Serena | Unity C# 工程索引准确性 |
| 持久代码地图 | Codebase Memory MCP、Aider repo map | 增量更新、查询质量、维护成本 |
| 架构约束 | ArchUnitNET、Roslyn Analyzer、架构决策记录（ADR） | 模块依赖检查与误报 |
| Unity 资源关系 | Unity AssetDatabase、Editor API | Scene 对象级依赖与动态引用 |
| 测试与运行 | Unity Test Framework、Profiler、命令行构建 | 可复现测试及场景验证 |
| 资产校验 | Blender Python、Unity 导入检查 | 模型/绑定/动画的定量检测 |
| 项目生产与审查 | GitHub Issues/PR、Notion；可研究 Kitsu | 依赖、交接与验收追踪 |
| 经验库/知识图谱 | Hindsight、Cognee、Graphiti、ADR 工具等 | 来源链、冲突与版本管理 |

不为堆叠工具而堆叠工具；任何新组件都应针对真实缺口提供效果验证。

## 经验研究的第一批真实样本

- **Massive Entertainment**：Feature Sign Off、跨专业依赖确认、资产生产与功能制作模式。
- **Valve / Half-Life 2**：Cabal 跨专业设计、快速原型与试玩；美术变化后的玩法回归。
- **Insomniac / Ratchet & Clank Future**：生产周期、可玩关卡、日常加载测试、构建稳定性与资源规划教训。
- **Double Fine / PsychOdyssey**：长周期创作、团队合作、设计变化与反复审查。
- **Hades、Subnautica、A Short Hike**：抢先体验、反馈驱动、独立开发范围管理。
- **《小王子》AI 3D 制作案例**：小体量 AI 辅助资产到可玩游戏的闭环；源码是否正式开源需另行核实。

研究每个案例时，务必记录原始链接、准确出处、直接证据和推论范围，不把工作室个别做法当作普遍规则。

## 初始验证场景

**场景 A：门与建筑**。给已有空间、构件和连通图的建筑系统新增开闭/上锁门。比较普通编码 Agent 与有项目认知工具的编码 Agent：能否先识别已有职责所有权，避免独立建立第二套空间拓扑、重复 Manager 和硬编码。

**场景 B：角色动画集成**。从已绑定模型到 Unity 动作、角色移动、战斗与测试，验证角色相关的代码/资源/运行地图是否帮助识别滑步、兼容性、接口和多专业交接问题。

**场景 C：完整可玩体验**。在多个独立子系统同时存在时，系统能否优先补齐集成、试玩和撤离/结算循环，而非不断新增局部功能。

评价维度：必要工作遗漏、重复抽象和状态源、架构违例、集成质量、真实运行成功率、返工次数、Token/时间成本与用户主观体验。

## 近期研究路线

1. 完善职业地图：从具体岗位的真实交付、判断、工具和失误案例切入。
2. 完善生命周期：把每个阶段拆到操作与验收，逐步建立专业工具/资料目录。
3. 深入公司调用链：按功能类型重建从提出到交付的真实流程与专业交接。
4. 建立经验蒸馏记录规范和少量高质量、有来源的样本。
5. 先验证代码/Unity 资源项目地图，再决定是否引入额外框架。
6. 使用对照实验检验工具增强是否减少重复架构、遗漏和集成失败。

## 决策状态

**已经确定**：项目目标、个人使用定位、三条研究主线、真实经验的核心地位、三条经验增长渠道、外部工具增强原则、项目全局认知与验证闭环的重要性。

**尚未确定**：Agent 框架与数量、数据库/图谱技术、所有候选工具是否适用、自动采集频率与预算、经验评分机制、正式数据 Schema、运行权限和自动化级别。

## 仓库原则

此仓库优先保存**经讨论确认的原则、研究证据、实验记录和待验证假设**；研究与实现分开，不擅自把候选方案标记为已经落地。
