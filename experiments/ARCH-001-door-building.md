# ARCH-001｜门与建筑：避免重复领域模型

状态：**待实验**。案例来自项目开发讨论；尚未读取《巨楼》当前仓库，因此不推断现有代码实际结构。

## 核心风险
编码 Agent 接到“实现门”后，可能独立新增 DoorManager/Registry/Connection/State 等，与建筑系统已有的空间、开口、构件注册和连通关系产生重复权威。局部测试通过并不能证明跨系统一致性。

## 对照任务
在**同一份已存在建筑模型与通行图的测试基线**上新增可开闭、可上锁的门。
- A：普通编码 Agent 与任务描述。
- B：相同模型与任务，增加只读代码/资源索引、职责地图、架构约束和历史决策查询。
- 控制模型、时间/Token/工具预算、初始提交；不允许将参考答案泄漏给 B。

## 先于开发的必须检查
1. 查出建筑空间、墙、开口、连接、门相关现存符号及具体引用。
2. 标记状态权威：几何/拓扑、门动态状态、通行判断分别来自何处。
3. 提供最小可行修改方案，论证每个新增抽象的必要性。
4. 评估 Prefab/Scene、AI 导航和交互的影响范围。
5. 定义静态结构、运行行为、集成和回归验收。

## 测试观察项
- 新增独立状态源/重复连通图数量；
- 新增管理器、硬编码或适配层数量及必要性；
- 相关原有接口复用比例（须按语义人工审核）；
- 引用完整性、运行通行行为、回归失败；
- 实际工程修改成本、返工次数、Token、时间。

## 结论规则
工具增强若只减少查询次数而降低最终正确率，不算成功。必要的新结构不能因“新增类数量多”自动判为错误；重点检查领域语义一致性、状态唯一性、可维护性和可玩效果。
